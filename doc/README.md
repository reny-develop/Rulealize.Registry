The first is a record of how the registry got its shape and is not binding on anybody. The
second is: it is what a submission is held to, and it is the half of the design record's §6
that has to be readable by the person opening the pull request.

That document is a design record in the sense
[Rulealize's `doc/`](https://github.com/reny-develop/Rulealize/blob/main/doc/README.md#the-design-record)
uses the term: it takes one subject, states the question it was written to answer, and
reports what was decided — including what is still open. It is not a specification, and
nothing in it has been built.

It lives here rather than in the Rulealize repository for the reason that repository already
applies to plugin specifications: a document belongs with the thing it describes, so that it
can change when that thing does and not on somebody else's release schedule. The registry is
not a design decision about the runtime, and the runtime should not be where its record is
kept.

The claim ledger they describe exists as data — [`ledger/claim.json`](../ledger/claim.json),
generated by [`tool/Ledger`](../tool/Ledger/) from a folder of plugin assemblies. One document
will join these, and it is not written:

- **the index format** — what a plugin entry and a rule set entry are, as JSON, and what CI
  checks about them. The ledger is settled; these are not, and they are not the same document
